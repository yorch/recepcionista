# Internationalization (English / Spanish)

The dashboard, onboarding, auth, billing, settings, calendar, calls, bookings, refunds and public pages (`/`, `/pay/[id]`, `/refunds`) are available in English (`en`) and neutral Latin-American Spanish (`es`, "usted"). No i18n dependency: Next 16's guide only describes routing and dictionaries, and the app has no locale in the URL.

## Pieces

| What | Where |
| --- | --- |
| Pure core: keys, `{param}` interpolation, `{n, plural, one {..} other {..}}`, `resolveLocale`, Intl helpers | `src/lib/i18n/core.ts` (client safe; ships no catalog) |
| Catalogs: one file per area with `en` and `es` side by side | `src/lib/i18n/catalog/*.ts`, merged by `en.ts` / `es.ts` (`es` is typed `Record<keyof en, string>`) |
| Server entry (both catalogs, `makeT`) | `src/lib/i18n/index.ts`; request helpers `server.ts` (`getLocale`, `getT`, `getCustomerLocale`) |
| Client provider and hooks (only the active language is sent) | `src/lib/i18n/client.tsx` (`useT`, `useLocale`) |
| API error string to message | `catalog/error-keys.ts` + `api-errors.ts` (`apiErrorMessage`, `errorText`) |
| Switcher | `src/components/ui/locale-switcher.tsx` (login, signup, forgot, landing, `/refunds`, `/pay`, onboarding header, sidebar, Settings) |
| Endpoint | `PATCH /api/me/locale {locale}` (users.locale + `rc_locale` cookie; CSRF-checked); business default: `PATCH /api/businesses/:id/settings {locale_default}` (owner) |

## Resolution order

`users.locale` -> `rc_locale` cookie -> `businesses.locale_default` -> `Accept-Language` -> `en`. `<html lang>` follows it; the CSP nonce is untouched (the layout is still rendered per request). Signup stores the request's language on the user and the business; an invitee starts in the business default (or their own cookie / browser language). `/pay` uses: cookie -> the booking call's language -> business default -> browser. Platform emails use the recipient's `users.locale`; texts to the owner phone use the first owner's locale (`ownerLocaleFor`); customer texts keep using the call language, else the business default.

Dates, times, money and phones go through `Intl` with the locale (`es-US`, USD). Phone numbers are shown as `(305) 555-0142`; `tel:` links keep E.164.

## Adding or changing text

1. Add the key to an area file in `catalog/` with BOTH `en` and `es` (`defineArea` fails to compile when one side is missing).
2. Use `t('area.key', { param })` (`useT()` in client components, `await getT()` in server ones).
3. New area file: add it to the generated import list in `en.ts` / `es.ts`.
4. Pure modules shared with the server (`kb/readiness.ts`, `components/knowledge/model.ts`, `call-handling-changes.ts`) take a `lang` / `locale` argument and carry inline `{en, es}` pairs.

## Tests

`tests/i18n-parity.test.ts` (same keys and `{params}`, plurals, keys used in source exist, error map), `tests/i18n-core.test.ts` (resolution, Accept-Language, plurals, Intl), `tests/i18n-emails.test.ts` (emails, banners, briefing), `tests/i18n-scan.test.ts` (fails on hard-coded English JSX text / user-visible attributes in `src/app` and `src/components`; allow-list inside), `tests/db/locale.test.ts` (PATCH endpoint, CSRF, signup, invites; needs `TEST_DATABASE_URL`).

## Residual English (known)

- Content written by people or models stays in its own language: call summaries, transcripts, flagged reasons produced by the voice tools, service and FAQ text the owner typed, business names, the seeded demo data and the demo console's caller lines.
- API error strings not in `error-keys.ts` are shown as the server wrote them; the audit log shows machine action names (`auth.login`).
- `NEXT_PUBLIC_PLAN_PRICE_DISPLAY` is operator text: set `NEXT_PUBLIC_PLAN_PRICE_DISPLAY_ES` (and `_ANNUAL_ES`) for Spanish, else the English text is shown.
- `global-error.tsx` (the root layout failed, so no provider) shows both languages.
- Voice-agent prompts, disclosure text and SMS keyword replies keep their existing per-call-language logic (`docs/verticals.md`); they are not driven by the dashboard language.
- Stripe Checkout / portal pages use Stripe's own language detection.

Console strings (agent A): the area `src/lib/i18n/catalog/adminConsole.ts` (prefix `ac.`) holds the `/admin` shell, review, history, system, overview, wizard and legal editor strings and the public legal page chrome. The **label and help of each registry setting** are not catalog keys: English lives on the registry entry and Spanish in `src/lib/admin-ui/setting-text.ts` (`tests/admin-console-ui.test.tsx` fails when a console-editable key has no Spanish text). The body of a legal page is operator-written markdown per language (`legal_page_versions`), served in the visitor's language with an English fallback.
