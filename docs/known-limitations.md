# Known limitations

Deliberate or accepted gaps in this release, so nobody discovers them in production. Each says what is missing, the
consequence and what the operator can do. Hardening fixed in review rounds 1-3 is in `docs/review/` (the reviews are point-in-time snapshots: several of their statements, such as "no CI" or "nothing schedules the briefing", were true when written and are not true now; `docs/changelog-hardening.md` maps every finding to its current state); this file lists what
remains. Not legal advice (see `docs/compliance.md`).

## Accounts and authentication (docs/auth.md)

- **No federated login (SSO/SAML/OIDC).** Sign-in is email plus password or a passkey (WebAuthn), with an optional TOTP authenticator app and recovery codes as the second step of a password login; there is no SSO/SAML/OIDC and no SMS second factor, so a company
  cannot bring its own identity provider or force its staff through one. A lost authenticator without recovery codes (and no passkey) needs an operator (`scripts/create-user.ts`, DB access) to reset.
- **No hard per-account cap on distributed second-factor guessing.** TOTP guesses are limited per (account, client IP), per pending session (5) and by a 10-minute pending lifetime;
  the per-account counter across IPs only logs (`distributed_guessing`) because blocking on it would let anyone lock a user out. A large botnet is slowed, not stopped. Mitigation: strong passwords, alerts on that log line.
- **Open signup needs a captcha in production** (Turnstile pair, or the explicit `SIGNUP_ALLOW_WITHOUT_CAPTCHA=true`). Without either, signup is refused and the product is invite-only. The opt-out leaves only rate limits and the hourly cap
  against bot farms. Turnstile depends on Cloudflare being reachable; verification fails closed, so a Cloudflare outage stops signups (invites and logins keep working).
- **The break-glass `ADMIN_TOKEN` cannot be revoked server-side** except by rotating it (its sessions can be revoked).
- Email is a root of trust: whoever controls the mailbox can reset the password (2FA still applies at login). No email deliverability monitoring beyond provider errors being logged.

## Deployment and scale

- **Single region, single Postgres, no read replicas.** Rate limits, leases, idempotency claims and the signup caps live in Postgres (`rate_limit_buckets`, `processed_events`, leases), so several app instances behind one database work,
  but multi-region or active-active is not designed. The background job runner (daily briefing at 18:00 per business time zone, hourly gratitude sweep, hourly cleanup, and the retention purge when enabled) runs inside every app process under Postgres leases and idempotency claims, so a second instance repeats nothing. It is a timer, not a queue: if every instance is down at 18:00 the briefing is caught up when one returns, but only until local midnight; the briefing-ready text is skipped in quiet hours and when the SMS cap is full. Work per pass is bounded (10 briefings, 25 gratitude sweeps), so very large installs catch up over several ticks. `JOBS=off` stops all of it.
- **Backups, restores, TLS termination and the reverse proxy are the operator's** (`DEPLOY.md`, `docs/runbook.md`). Per-client rate limits need `TRUSTED_PROXY=true` behind a proxy you control; without it all clients share one bucket.
- **Plain-HTTP staging** works only with `CSP_UPGRADE_INSECURE=false` or an `http://` `APP_URL` (otherwise browsers upgrade subresources to HTTPS and fail); Twilio, Stripe and ElevenLabs call back over public HTTPS, so a staging box that must receive their webhooks needs HTTPS anyway.
- `NEXT_PUBLIC_*` values (Turnstile site key, plan price text) are inlined at build time: changing them needs `./deploy.sh` (a rebuild), not a restart.

## Telephony, voice and messaging

- **Twilio Advanced Opt-Out / default long-code STOP handling** can block a number at Twilio (error 21610) without forwarding the STOP to `/api/sms/inbound`, so the app's suppression list only knows STOPs it saw. Matching is on E.164;
  anything ambiguous is over-suppressed rather than texted (`docs/compliance.md`). Keep Twilio's own opt-out handling on and reconcile in the Twilio console.
- **Provider-side retention needs operator settings.** ElevenLabs conversation retention / zero-retention, audio saving, Twilio recording and message-log retention, and the LLM provider's no-training settings are configured by the operator in each console
  (`docs/runbook.md` section 5). The app does not set them, cannot verify them, and does not purge provider-side recordings/transcripts (declined calls: best effort). Retention shorter than post-call delivery would break the transcript webhook.
- **Several ElevenLabs API call shapes are unverified best effort** (the conversation-initiation webhook configuration on workspace/agent, and, for tenant release, detaching the shared phone number from an agent before deleting it). Failures are logged and the runbook says what to check by hand.
- **Number provisioning is US-only; the area code is the owner phone's own (when a valid US/Canada number), else `TWILIO_AREA_CODE` (default 305).** The Twilio account is shared by all tenants: a purchase whose answer is lost is adopted only if the number carries this attempt's FriendlyName tag, so a purchase that Twilio completed but never confirmed AND whose listing is still missing after ~13 s of retries is left unadopted (an operator finds it in the Twilio console via the `provision.number_failed` audit row; a retry buys another number). When Twilio search/purchase fails (or in production without Twilio credentials) provisioning FAILS with a 502/503 and the business stays `onboarding`; no fake number is ever issued there (the mock-pool number exists only outside production with no Twilio credentials). A purchase whose answer was lost is looked up and adopted, and a number bought before a later failed step is kept and reused by the retry. A tenant outside the US needs an operator-assigned number. Provisioning imports each purchased number into ElevenLabs and binds it to that tenant's agent (`ELEVENLABS_PHONE_NUMBER_ID` is only a single-line fallback and is never moved between tenants); the import, bind, delete and register-call shapes are UNVERIFIED against a live account (one file, `src/lib/voice/elevenlabs-phone.ts`, runbook section 8), so the first real tenant must be checked by hand.
- **Customer texts to the business number** are stored in the dashboard inbox (Messages), texted to the verified owner phone (not in quiet hours, within `INBOX_FORWARD_HOURLY_LIMIT` per hour) and acknowledged once per sender per 24 h. A message that arrives in quiet hours or beyond the hourly budget is NOT texted to the owner later: it waits in the inbox (the sidebar badge counts it). Per-sender (10/h, checked first, so one number can only spend its own budget) and per-business (300/h) flood limits drop the excess without storing it; at most 2 owner texts per sender per hour (the rest waits in the inbox). A text that looks like an opt-out request ("don't text me again", "remove me", "Stop. Who is this?") gets NO automatic reply, is flagged `possible_opt_out` and the owner is told (one tap to opt the number out); an inbound text from a Caribbean / territory / premium NANP number is stored and forwarded but never answered, and a manual text there needs a booking. **Texts go out from the tenant's own Twilio number** (so STOP and replies reach that business); the shared `TWILIO_PHONE_NUMBER` is only the fallback (a tenant with a mock-pool / no number, a number Twilio refuses as a sender, owner verification codes), and a customer reply to it is attributed to the business that texted them last in the last 30 days (a customer texted from the shared sender by two businesses is attributed to the latest for conversation, and a STOP applies to all of them). Residuals: US carriers filter unregistered A2P 10DLC numbers (register the tenant numbers, `docs/runbook.md` section 8); the owner forward quotes up to 140 characters of the customer's words in the SMS the owner receives (the platform's own log keeps none of it). Reviews 20 H1 / H2. A sender with no call or booking can be answered from the dashboard but not through the owner call-in voice channel (`owner_replies` only references a call or a booking; supporting a message-only lead needs a schema change). The auto-reply language is guessed from the text (Spanish/English word hints), else the business default. UNVERIFIED against a live Twilio account: the inbound webhook field names (`MessageSid`, `From`, `Body`) and that an app-sent reply to an inbound message is billed like any other text.
- **Languages: English and Spanish for the agent and texts; the dashboard, auth pages, emails and owner texts are available in English and Spanish** (`docs/i18n.md`; the Spanish copy has not been reviewed by a native speaker, and call summaries, owner-typed content and operator price text stay in their original language).
- **SMS caps count segments, not sends**, using the GSM-7/UCS-2 rules of `smsSegments` (a two-unit character is never split across segments, as on a handset). Carriers can still differ on exotic edge cases (national-language shift tables), so the count can differ from the Twilio invoice by a segment; inbound-reply auto-answers sent by Twilio are counted from our own reply templates. Trial caps (`TRIAL_SMS_CAP`, `TRIAL_CALL_MINUTES_CAP`) apply only while billing is enforced.
- **Usage metering is reconciled, not instant.** Call minutes are added once per conversation, by whichever arrives first: the post-call webhook or the `reconcile` job (`src/lib/voice/reconcile.ts`), which fetches the duration of a call (customer or owner line: owner calls use AI minutes too, they are only never blocked by the cap) older than `RECONCILE_AFTER_MINUTES` (20) with no post-call from ElevenLabs, backs off exponentially, and gives up after `RECONCILE_MAX_ATTEMPTS` (5) with an audit row `voice.reconcile_gave_up` and an error log (that call's minutes are then never counted: look at it by hand). Until it runs, the cap can briefly under-count. Over-cap calls are cut to 60 s by the initiation override (needs that override enabled on the agent); the cap is not enforced mid-call for calls already running. UNVERIFIED: that the conversation endpoint reports `metadata.call_duration_secs` for a call whose webhook was lost (docs/runbook.md section 6 check).
  Over-cap calls are cut to 60 s by the initiation override (needs that override enabled on the agent); the cap is not enforced mid-call for calls already running.
- **Emergency handling is advice plus an owner alert**, not dispatch. The agent tells the caller to hang up and call 911 and alerts a verified owner phone; an unverified or opted-out owner phone gets no alert (the agent says so honestly). Because these alerts are exempt from the SMS plan cap they have their own per-business hourly budget (`OWNER_ALERT_HOURLY_LIMIT`, default 6; the first emergency of a call may go to 2x): a caller who makes the agent raise many different alerts gets an honest "could not reach the owner" once it is spent, and the owner is told at most once about identical alerts for a call. Alerts are cut to 320 GSM-safe characters (accents and dashes are transliterated).
- Owner privacy tools (Settings, "Customer privacy") look up, export (JSON) and erase one customer by phone number, using the same functions as `/api/privacy/*`; erasing is permanent and the export is built in memory (a customer with a very large history makes a large download). Provider-side copies (Twilio message logs, ElevenLabs conversations) are not touched (see the retention note above).
- No do-not-call scrubbing, no written-consent capture UI for follow-up/review texts, no HIPAA/PCI scope, no data residency controls (`docs/compliance.md`, "Out of scope").

## Billing (docs/billing.md)

- **Stripe only, a monthly plan and an optional annual plan** (`STRIPE_PRICE_ID_ANNUAL`) with per-business SMS/call-minute caps. No usage-based billing or seat pricing; invoices and tax are whatever Stripe provides. Switching between monthly and annual happens in the Stripe Customer Portal (it must be configured to allow plan switching between the two prices); the app learns the cadence from the subscription webhook, so the badge can lag a switch by a few seconds. Onboarding and the Billing page both offer Monthly / Annual when `STRIPE_PRICE_ID_ANNUAL` is set.
- **Free trials are limited per card fingerprint and normalised email**, which stops casual repeats but not someone with many distinct cards and addresses.
- **Released tenants lose their number for good.** The `tenant_release` job (same logic as `scripts/release-canceled-tenants.ts`) releases a canceled tenant's Twilio number and ElevenLabs agent after the grace period and a heads-up mail; a later resubscription is provisioned with a NEW number. The
  workspace-wide ElevenLabs tools are shared by all tenants and are only removed when the last agent goes. A business with no owner email is not released automatically (admin API with `skip_notice`). The job is a DRY RUN unless `TENANT_RELEASE_JOB=on` (`report` runs the daily dry-run report; `off` = manual dry runs only, a real run is refused), releases at most 10 tenants per run, and its state is audit-only (`jobs.tenant_release_report`, `billing.release_notice`, `billing.tenant_released`; `GET /api/admin/jobs` shows the newest report). Nothing releases on its own until an operator sets `TENANT_RELEASE_JOB=on` after reading a dry run. The single-business admin route `POST /api/admin/release-tenant` is a deliberate, per-business action and is not gated by that switch.
- Comped (grandfathered/admin-set) accounts are never released or billed by the app; they are an operator decision to revisit.
- `BILLING_ENFORCED=false` is a supported opt-out but disables caps and plan checks for existing tenants; do not combine it with open signup.

## Data, privacy and operations

- Retention (`RETENTION_JOB=on`) purges calls, transcripts, SMS bodies, briefings and nulls booking PII after `retention_days`; opt-outs are never purged. It is off by default so an upgrade cannot silently delete data.
- Audit events are append-only and not purged by retention; their metadata avoids secrets and message bodies (secret-looking keys are redacted) but contains actor and business ids, client IPs and, for releases, the last 4 digits of the number.
- Database migrations are forward-only; rollback means restoring a backup (`docs/runbook.md` section 4).
- Accepted advisories in dev/CLI-only transitive dependencies are listed in `docs/dependencies.md`.
- Tests run against a scratch Postgres and fake providers; **no automated test places a real call or sends a real SMS/email**. `bun run verify:deploy` and the manual live test-call protocol (`docs/runbook.md` section 2) cover the real wiring.

## Call handling, calendar and roadmap (this release)

- **Native-line live transfer (`NATIVE_TRANSFER`, default OFF) is unverified against the live provider.** With it off, forwarding does not exist on the native ElevenLabs line (the platform answers before our code runs): the dashboard says "Forwarding is not available on the AI voice line", the Forward choice is disabled and callers hear the paused script. With it on, the agent carries the ElevenLabs transfer-to-number system tool whose destination is the dynamic variable `transfer_destination`, set PER CALL by the initiation webhook only to the verified, re-vetted forward number (docs say a destination "can be typed directly or as a dynamic variable"; the exact `transfer_rules` / `provider_configs` shape and that the variable resolves inside it are unverified: run the live transfer test in docs/runbook.md section 8 first). Residual limits: (1) the talk time AFTER a transfer is not visible to us (post-call reports the AI part), so it is metered as forward seconds from that report only and the concurrency lease is freed at post-call, not at hang-up; (2) a prompt that skips the `transfer_to_human` tool is bounded only by the destination being empty or valid (the caps and per-caller limits are charged in the tool and, for a due Forward, at initiation); (3) transfers cannot be capped to the minutes left (no `timeLimit` on the platform's transfer); (4) turning the flag off does not remove an already-provisioned transfer tool from existing agents until they are re-provisioned, but the destination variable is then always empty, so nothing can be transferred; (5) the outcome (`connected` / `failed`) is read from the post-call transcript tool calls, an UNVERIFIED shape.
- **Carrier voicemail on a forwarded leg (webhook line) is handled by call screening.** The owner's leg is whispered "<business> call from <number>. Press 1 to accept"; no input / any other key hangs up that leg only, the call is treated as unanswered and the caller gets our voicemail, and only bridged seconds are metered (`src/app/api/voice/screen`, `voice/screening.ts`). Residual: the owner must press 1 on every forwarded call (a conscious trade-off; there is no per-business off switch); UNVERIFIED against live Twilio: whether `DialCallDuration` already excludes the whisper (we subtract the measured whisper time) and what `DialCallStatus` a hung-up whisper reports (we do not depend on it: a screened leg that was not accepted is always unanswered). The 20 s ring time, the 6 s minimum answered time and the caps remain as defence in depth.
- **Per-caller limits and the known-customer reservation trust STIR/SHAKEN, not the caller id.** Only attestation-A callers (Twilio `StirVerstat`, stored on `calls.stir_status` / `caller_verified`) get their own budget and the reserved share; B, C, unverified and failed callers share the stranger bucket (failed: a stricter one), so spoofing a known customer's number no longer burns their budget or their reserved capacity. Residual: a real known customer calling from a number with no attestation (many non-US and some VoIP carriers; and the whole NATIVE line, where ElevenLabs does not document passing a verstat in the initiation webhook, so absent = stranger treatment) is treated as a stranger and can be refused when the stranger share is spent; `STIR_TRUST=off` restores caller-id identity for deployments where that is the wrong trade. A flood from many different numbers is still bounded by the stranger share and the hourly business budget. Callers that withhold their number share one bucket.
- **Usage recorded before the round-6 migration is not split.** Forward and voicemail seconds of the month the migration ran in stay in `call_seconds` (they cannot be told apart); the three counters are exact from the next call.
- **Recording deletion at the provider waits for the provider.** Until the queue drains (`pending_recording_deletions`) an erased customer's recording still exists at Twilio even though no row in the app points to it; the erasure response and the export say so. Nothing outside the app (a Twilio console user, a Twilio-side export) is touched. A cascade delete of a business outside the app's own paths (a manual SQL `DELETE FROM businesses`) does not queue recordings.
- **`/api/voice/incoming` is a webhook line, not the production AI line.** A signed Twilio call always gets TwiML; the AI is connected only through ElevenLabs' register-call TwiML (UNVERIFIED shape, `ELEVENLABS_REGISTER_CALL=off` disables it), otherwise the caller gets an honest voicemail. Importing the number into ElevenLabs (the default per-tenant line) remains the supported way to get AI calls. The owner call-in line on a webhook line works only through the same register-call path.
- **Forwarded minutes are the bridged seconds** of the dialled leg (the inbound leg's own Twilio cost and ringing time are not counted); they come from Twilio callbacks, so a lost callback after retries means those minutes are not counted. Voicemail audio length is counted from Twilio's `RecordingDuration`.
- **Voicemail audio stays at Twilio** until the retention purge (needs `RETENTION_JOB=on`) or a customer erasure deletes it there (best effort, logged); with the purge off, recordings are kept.
- **Step-up re-authentication** exempts the break-glass admin token / cookie and `ALLOW_INSECURE_DEV` (they carry no password); pre-existing sessions have no recent-auth stamp and ask for the password once.
- **Paused prompt override** (`ELEVENLABS_PAUSED_PROMPT_OVERRIDE`) uses an UNVERIFIED ElevenLabs override field and is off by default; the enforcement that matters (every tool except taking a message is refused) is server-side.
- **Refunds are owner-initiated and one per booking** (docs/refunds.md): cancelling texts the customer and offers the refund by policy but never refunds by itself; a second (partial) refund of the same booking must be made in Stripe; a deposit paid before payment ids were captured must be refunded in Stripe; a dispute is audited, alerted and shown on the booking (`dispute_status`) but never contested by the app. A customer's text reply `C` cancels their ONLY upcoming booking (several: they are asked to call); `CANCEL`/`END`/`QUIT` are opt-outs by Twilio's rules and are not cancellations.
- **Reschedule** (calendar panel and the `reschedule_booking` voice tool) moves one booking at a time to a free slot on the business's configured grid (Settings > Scheduling: 15/30/60 minutes); it does not change the service or the length from the dashboard, and the voice tool refuses after 3 moves of the same booking. A change the owner makes at night is not texted until the owner presses "Text the customer" (no automatic retry).
- **Recording player** plays ElevenLabs conversation audio through `/api/calls/:id/audio` only for calls with `consent_status = 'disclosed'`. UNVERIFIED: the provider's response content type and Range support (the docs list the endpoint only), so the whole file is read once (max 40 MB) and kept in memory for 60 s to answer seeks. It exists only while the provider keeps the audio (ElevenLabs retention / audio saving settings, runbook section 5). Memory is bounded: the body is streamed with a hard 40 MB cap whatever the headers say, parallel requests for one recording share ONE download, at most 4 downloads run per process (a fifth request gets 503 + `Retry-After`) and the 60 s cache is capped at 64 MB in total. Erasure and the retention purge DELETE the provider conversation (audio and transcript) through the durable queue (next bullet) and drop the memory copy.
- **Provider conversation deletion (ElevenLabs).** Customer erasure, the retention purge and the demo reset queue every erased call's `conversation_id` in `pending_recording_deletions` (`provider = 'elevenlabs'`, same transaction as the call-row DELETE; only when `ELEVENLABS_API_KEY` is set); the jobs runner calls `DELETE /v1/convai/conversations/{id}` (documented; removes the audio AND the transcript) with retries and backoff, a 404 counts as gone, and an alert (`recordings.deletion_stuck`) fires after 5 failed attempts. A declined or owner call whose inline delete failed is queued the same way. Limits: the app cannot see or purge copies ElevenLabs keeps in its own backups or logs, and an ElevenLabs workspace that has the conversation already auto-deleted answers 404 (treated as done).
- **Voice selection** offers the operator's allowlist (`ELEVENLABS_VOICE_ALLOWLIST`) or the provider's premade voices; the picker is disabled without an ElevenLabs key. Previews are the provider's own samples (`preview_url`, host unverified, fetched server-side). The TTS field used is `conversation_config.tts.voice_id` (documented); a re-sync the provider rejects leaves the choice saved and the call voice unchanged (`synced:false`).
- **Minimum content checks** gate provisioning for non-admins (3 priced services, opening hours, 1 FAQ). They count what is stored; they cannot judge whether it is right. A business already live is not re-checked. Admins override.
- **Calendar**: week starts on Sunday for US/CA/MX-style businesses, Monday elsewhere (viewer can switch, stored in the browser). Jobs that cross a DST jump are stretched or squeezed by the skipped hour; overnight opening hours are not supported.
- **Live transcript** (`/dashboard/calls/[id]`, Today "Live now") polls the ElevenLabs conversation endpoint (documented; that `transcript` is filled while `in-progress` is UNVERIFIED, docs/runbook.md section 6). Lines can lag by about 2-4 s, there is no monitoring-websocket source (the plan/docs could not be confirmed; add one behind `LiveTranscriptSource`), SSE connection limits are per app instance, and the post-call transcript replaces the live lines afterwards. A caller's objection is detected by the same phrase list as the post-call (so the very first line may already have been shown); nothing is stored before consent is `disclosed`.
- **Owner voice reply (built, with limits).** The owner can ask by phone who called and have the assistant text one customer back after a YES code (`docs/owner-call-in.md` "Voice reply"). Limits: messages are at most 120 characters of plain words (no links, numbers, codes, payment requests); at most five leads per list (calls and bookings of the last 7 days, one per number) and, per caller-identity class, at most 10 (unverified) / 30 (verified) distinct leads a day, only with kind, first name, last 4 digits and time, never what the customer said; a sent text cannot be undone; quiet hours (9 PM to 8 AM, business zone) refuse the text instead of queuing it; one text to a customer per identical wording per hour and two per hour in total; the message scanner reads a normalised copy (NFKC, Unicode digits, spelled digits, vanity numbers, links in words, spaced or leetspeak brand names, non-Latin letters) but wording that expresses a number or a payment outside every pattern can still pass (the owner sees the exact words in the confirmation text, and this is not a defence against a compromised owner phone); a spoofed owner caller id that reaches the line can hear first names, last 4 digits, kind and times of at most about 10 distinct recent leads a day and hide at most 5 from other unverified callers (never from a verified owner call), and cannot send anything, unless `OWNER_REPLY_REQUIRE_ATTESTATION=true` (turn it on for health-adjacent verticals when the carrier gives attestation); the data export of a customer (`privacy.ts`) does not yet include `owner_replies` (erasure and retention do); a crash after the YES claim, or a provider timeout, leaves the reply `uncertain` (the reconcile job moves a stale `sending` row there; it is never retried, counts toward the daily cap and the duplicate guard, and the dashboard says "unknown: check before resending"); a failure AFTER the provider accepted the text keeps it `sent`; UNVERIFIED: how the platform fills `lead_ref`.
- **Owner call-in changes are real settings now, with limits.** Hours, holiday closures (`businesses.closed_dates`, at most 366 dates) and the service area are applied to the real fields by a confirmed change (SMS YES code) and undone only while nobody edited them since (`changed_since`); a change proposed before a dashboard edit of the same field is refused as stale. Not supported by phone: overnight hours, several windows per day, closing the whole week (dashboard only). The tool arguments `days` / `dates` / `areas` are arrays in the ElevenLabs tool schema: UNVERIFIED that the live platform fills array parameters the way the schema declares (check with the owner test protocol, docs/runbook.md section 9). Past closures are dropped when the next closure is added; the calendar view does not shade closed dates.
- **Dashboard edits reach the live agent (and may be late).** A knowledge-base or business (name, hours, service area, website, owner name) edit rebuilds the stored prompt and pushes it to the ElevenLabs agent immediately. If the provider call fails the edit is saved, the business is queued for the `reconcile` retry (`agent-dirty`), and the dashboard says "saved, but the live receptionist could not be updated yet" instead of "she will use this on the next call".
- **A text is never "delivered" off a mock in production.** Without a complete Twilio configuration production texts fail with `sms_provider_not_configured` (verification routes answer 503; nothing is metered, no follow-up consent is recorded, the voice agent does not say it texted). Outside production a mock counts as delivered (dev and tests only).
- **`POST /api/admin/resync-agents` re-pushes agent config and tools, it does not verify them.** The provider's stored state is never read back (no documented read of the final config), so a run reports what the provider ACCEPTED. A dry run never calls the provider.
- **Mock providers need a non-production process.** A production build refuses mock Google / mock checkout / the log email provider by design (several checks are inlined at build time), so a mock end-to-end run needs `next dev` (docs/runbook.md section 11). Provisioning in mock mode stores no agent id (set one by hand to drive the voice tools).
- **Mock number detection** (`isMockPoolNumber`) is derived from the number shape, not a stored flag; those numbers exist only outside production without Twilio credentials.
- **Verticals are templates, not verified trade knowledge** (docs/verticals.md). The seven packs (hvac, plumbing, electrical, cleaning, landscaping, dental, general) carry starting services, prices, FAQs, emergency rules and wording that have not been reviewed by a person in each trade: owners must check every line on the review step, and going live REQUIRES the owner to confirm the services (names, prices, durations, descriptions), FAQs, pricing notes and service area (`content_confirmed_at` + a fingerprint: a later change of any of them, FAQ answers included because the templates put prices there, makes the confirmation `stale`; the Knowledge card sends the fingerprint of the content it showed and the server refuses with 409 `content_changed` when the stored content differs, e.g. after a concurrent staff edit; UPGRADE NOTE: confirmations stored before the FAQ coverage become `stale` once and must be confirmed again; the owner must save edits before confirming, the card confirms what is SAVED and the receptionist cannot be turned on again until it is re-confirmed; a business that is already live is not re-gated). The template never invents a service area: it starts empty and is required. Prices are illustrative US starting points. The dental pack is not a HIPAA-compliant product (PRD non-goals): the prompt tells the agent to note only an insurance plan name and never member or card numbers, but call recordings and transcripts may still hold health details the caller says. Changing the vertical later does NOT replace the owner's services, prices or FAQs (they may still describe the old trade); it rebuilds the prompt, the call script when it was never edited, and re-syncs the agent. Cleaning, landscaping and general have no emergency triage by design (the 911 life-safety rule and a small universal danger-to-life keyword list still apply). The demo business, its seeded calls and the demo console's canned transcripts (`src/lib/demo/seed-data.ts`, `/api/demo/simulate-call`) are HVAC; only the summary prompt follows the business vertical. Spanish seeds are used for a business whose default language is `es`; the dashboard itself is bilingual (docs/i18n.md). The workspace-wide `flag_emergency` tool description is trade-neutral and relies on the prompt's EMERGENCIES section.
- **Structural refactors not done** (no behaviour change, risk on paid-resource paths): extracting `provisionBusiness` from the provision route; replacing the remaining raw hex colours with design tokens everywhere; no automated accessibility audit in CI (the new calendar, panel and switch are keyboard and label tested by hand).
- **`/pay/[id]` is a bearer link** (unguessable booking UUID). In production it never renders a card form: a live Payment Link redirects to Stripe, a paid booking shows a receipt (service, amount, business, date; no card digits, no claim of a text), anything else shows "this link is not available". The Stripe lookup is cached 60 s with a per-process budget of 60 lookups a minute; over it the page answers "not available" until the window passes. A customer is not sent a receipt text.
- **Deposits** (docs/review/18f #17/#18/#24, Phase 2 agent C): the amount is computed on the server from the business's deposit policy (Settings > Deposits). The AI cannot choose it, and with the policy off it cannot ask for a deposit at all; the AI line still caps at $500 (the owner policy limit is $1000). The currency is still USD and card only (Stripe Payment Link). A deposit the owner marks as paid manually is never refunded through Stripe: the owner refunds it off-platform and records it. A Stripe payment that arrives after a manual mark (the customer paid the still-live link) REPLACES the mark: the booking becomes a card deposit (refundable through Stripe, manual refund bookkeeping reset, the manual refund stays in the audit trail), the owner is always texted that the customer paid twice and audit `payment.paid_over_manual_deposit` is written; marking a deposit paid queues a durable deactivation of the open link (also found by `booking_id` when its id was never stored); a stale snapshot cannot rewrite the amount of a paid deposit and a link created for a booking paid meanwhile is deactivated at once. The AI only asks for a deposit for a booking made on THIS call (the call's single booking is attached automatically), and a percentage deposit uses the owner's CATALOG price of the service (no catalog price = no AI deposit), never the model's estimate. A demo checkout leaves `deposit_source` empty. Per-service deposit amounts are not modelled (one policy per business; a percentage uses the booking's price estimate).
- **Dashboard bookings** use the same checks as the AI. A booking made without a phone number can be created and edited but cannot be texted (no confirmation, no deposit link by SMS; the owner can copy the link). Notes are not stored on a booking (the call summary is the only notes field).
- **Plan price** shown on Billing, onboarding and the landing page is read from Stripe (`STRIPE_PRICE_ID` / `STRIPE_PRICE_ID_ANNUAL`, cached 10 min); when Stripe is unreachable the operator's `NEXT_PUBLIC_PLAN_PRICE_DISPLAY*` text is shown instead. Only a single plan exists (no tiers). The caps listed are the ones the metering enforces (`PLAN_*`, `TRIAL_*` env).
- **Deploy**: no reverse-proxy rate-limit middleware ships in compose (the app has its own Postgres limiter); `deploy.sh` still sources `.env` as shell, so values must be shell-safe.

- **Language (docs/i18n.md).** The UI, platform emails and owner texts are English / Spanish. Model- and caller-written content (call summaries, transcripts, flagged reasons), owner-typed KB text, unmapped API error strings and operator price text stay as written; the audit log shows machine action names. Spanish copy is machine-assisted and has not been reviewed by a native speaker.

## Residuals of reviews 11-15 (what is left after the residual-gaps pass)

Fixed since they were first documented (see `docs/changelog-hardening.md`, "Residual gaps"): owner call-in budgets per caller-identity class; events left in a previous Google account; pre-upgrade owner proposals; transferred-call metering fallbacks and the retry of a failed forward write; the usage-warning job visiting every business; the stale call script after a vertical change; a refund pending forever; payment links texted before the upgrade; "Sign out of this business". What remains, and why:

- **Owner call-in, spoofed caller id (reports 11 L4, 12 L6).** Sessions (10 a day), confirmation texts (6 an hour) and the attack lockout (5 flagged proposals, 1 hour) are now kept per identity class: STIR attestation A is `verified`, everything else `unverified`, so a spoofer can no longer use up the budget of an A-attested owner call. Still true: a call whose caller id equals the verified owner number and whose verdict is not `failed` gets the private owner assistant; it can only RECORD proposals, every change needs the YES text from the verified phone, every text names the time of the call and carries "Not you? Reply NO", and only applied changes are read out. A real owner whose carrier gives no attestation shares the unverified class with any spoofer (the dashboard is the fallback while that budget is spent; the native line passes no verdict to us at all, so every native-line owner call is `unverified`). No owner PIN: it would be spoken over a line we assume is spoofable (replayable) and the SMS from the verified phone is already the second factor.
- **Previous Google account events (report 11 M1).** The events that cannot be deleted (the old tokens are dead, which is the usual reason for reconnecting) are now listed on the Google card ("N events from the previous account could not be removed. Remove them in Google Calendar.") until the owner dismisses them. We cannot delete them for the owner: no token is kept after the switch, by design. The list holds the service and start time of the booking (never the customer's name, phone or address); the events themselves still contain what was pushed (customer first name, phone, address, notes) in the owner's old calendar, so the owner must remove them there. Customer erasure blanks the service of the listed row. The row is a reminder, not a verification: if the owner deletes the event by hand nothing tells us, they dismiss the card.
- **Transferred calls (reports 12 L2, 15 L3).** The AI / forward split of a connected transfer uses the transfer turn's `time_in_call_secs`, else the bridged duration of a Twilio dial-status callback, else the last timed turn before the transfer, else the whole call is forward time. The provider's transcript shape and whether ElevenLabs' own transfer leg ever calls our dial-status route are still UNVERIFIED against the live service (on the native line it very likely does not, so the last two fallbacks are the ones that matter). A transfer whose result cannot be read stays `attempted` and is metered as an ordinary AI call. A forward write that failed after the AI part was recorded is marked on the call (`forward_pending_secs`, with the metering key it was written under in `forward_pending_key`) and finished by the `reconcile` job; it is deduplicated per key, so a callback that metered the leg first, or a call sid filled in later, makes the retry a no-op. When the post-call webhook never arrives, the reconcile job meters a transferred call (connected, or a dial duration was reported) through the same split: only the AI part counts against AI minutes and the forwarded leg goes through the per-sid forward metering (report 17 M5); with no transcript, no dial duration and `connected` the whole call is forward time.
- **Refund pending forever (report 13 H2).** "Check with Stripe" (owner, step-up) and the `reconcile` job (pending longer than `REFUND_RECONCILE_AFTER_HOURS`, default 6) list Stripe's refunds for the payment and adopt the refund Stripe has or mark the attempt failed when Stripe has none and the attempt is at least 30 minutes old; they never create a refund. UNVERIFIED against a live Stripe account: the `GET /v1/refunds?payment_intent=` list shape beyond the fields used. A refund made in the Stripe dashboard is recorded as pending by the webhook (its Stripe id is stored on the booking) and the check matches the booking's own refund by that id first, whatever its amount or metadata, so it is never called "never reached Stripe"; if Stripe lists a LIVE refund on the payment that this app did not make for the attempt and none of the booking's own is found, the check answers 409 `foreign_refund` and changes nothing (look at it in Stripe). "Never reached Stripe" also needs the age gate when only an OLDER failed attempt is listed (only a refund created at or after the current attempt counts as it). Clicking Refund while a refund that was not made here is processing is refused (409 `in_progress`). A refund pending for a different amount than the booking's can still only be changed once it fails or finishes. The pass looks at the least recently checked refunds first (rows looked at in the last hour are left out in SQL), so refunds Stripe keeps processing cannot starve newer stuck ones.
- **Payment links texted before the upgrade (reports 13 L1, 17 M4).** Cancelling never waits for Stripe and never pages Stripe inline (dashboard, customer SMS and live voice cancels alike): only a booking that had a deposit link attempt (a stored link id, or a texted `payment_link` message) is queued, the first attempt runs in the background with 4 s request timeouts, and the `reconcile` job retries a failed one for up to 3 days. A stored id is deactivated directly; with none stored the booking's links are looked up by `booking_id` metadata (and `business_id` when present), at most 2 pages of 100 newest active links and 6 s, audited with `via: stripe_lookup`. Stripe has no metadata filter or search for Payment Links and the platform account's active list holds every business's links, so an old unstored link beyond the newest 200, or one whose metadata was never set (very early builds), is not found; it stays payable, but a payment for a cancelled booking still alerts the owner and reopens the refund. Links are always stored from now on, so this only affects links texted before the id was stored.
- **Usage-warning job (report 14 L6).** It now visits only businesses whose usage counter changed since the previous pass (with a 2 minute overlap; oldest change first, and when more than 5000 changed the next pass continues from the last one read instead of skipping the rest), plus those with a warning that was deferred, failed or hit an error (a durable retry marker kept until a clean visit), and does a full sweep on the first pass and at least daily (which also covers a cap that was lowered). The inline trigger on every usage write is still the primary sender; warnings stay exactly-once (`markWarned`).
- **Vertical change call script (report 14 M2).** The `agent-dirty` retry now also rebuilds the GENERATED call script (empty, or identical to what any vertical generates for these services) from the current vertical, so it no longer stays the previous trade's; an owner-edited script is never touched, a script generated for an older services list is still recognised (the header line is ignored), and the write is a compare-and-swap so an owner edit saved between the read and the write wins. If the retries also give up (8 attempts, an audit row and an error log say so) an operator runs `POST /api/admin/resync-agents`.
- **Sessions (reports 15 L5, 17 M3).** Accepting an invitation lifts the sign-out only for the session that accepted it; the person's other sessions stay revoked until a new login (a re-grant is not their consent). "Sign out of this business" now also marks the person's other sessions (`revoked_business_ids`): they cannot act in or switch back to it until they sign in again; disabling or removing a membership does the same. Not done: it does not sign the person out of their OTHER businesses (an owner has no authority there), and the marker is per session, so a session created AFTER the sign-out (a new login) works normally by design.
- **Pre-upgrade owner proposals (report 11 M2).** At apply, a proposal whose base does not cover every knowledge-base field it touches (anything stored before the upgrade) is refused like a stale one (status `rejected`, `owner_kb.stale` audit): the owner asks again. They expire after 30 minutes anyway.

## Platform D: scheduling, time zone, briefing audio, LLM, tenant jobs

- **Time zone is inferred from the owner's phone area code only as a suggestion.** Area codes straddle zones (850/448, 308, 812/930, 208/986, 541, 906 give no suggestion) and mobile numbers travel: the suggestion pre-selects the list in onboarding while the zone is still the untouched default (never over a zone the owner already chose) and in Settings, but the owner saves it. A legacy non-IANA zone name from before the zone setting existed was mapped by the migration to its IANA zone (`PST8PDT` to Los Angeles, `GMT` to UTC, `Japan` to Tokyo ...) or, when unknown, to New York, and every repaired row has an audit event `business.timezone_repaired`. Existing bookings are absolute instants and never move when the zone changes; `hours` and `closed_dates` are wall-clock times in the NEW zone, so the owner is told to re-check them. The list covers the US and Canada; other IANA zones set through the API are kept and shown.
- **Scheduling configuration** (slot length 15/30/60, minimum notice, booking window, buffer, crews) applies to offers, the voice tools, AI / public bookings and customer moves. Bookings the owner adds or moves from the dashboard skip the notice and the window (never the hours, buffer or crews), and the dashboard's slot lists offer exactly that; the window counts today (`horizon_days = 1` is today only, 14 is today and the next 13 days). The voice agent says why a day has nothing (beyond the window, closed, past or full). The buffer is kept clear in code (and around Google Calendar blocks); the database constraint only guarantees raw non-overlap per crew, so `enforce:false` (an explicit override) skips the buffer but never the overlap. A start time is not forced onto the slot grid when a booking is created (the AI is offered grid times; the owner may book any minute). Crews are interchangeable (no per-crew skills, hours or names); lowering `crews` is refused while an upcoming booking sits on a higher crew.
- **Briefing audio needs `ELEVENLABS_API_KEY`.** The ElevenLabs text-to-speech call (`POST /v1/text-to-speech/{voice_id}?output_format=mp3_44100_128`) is UNVERIFIED against the live API in this repository (tests use a stub). Without the key, or when the provider fails, the briefing has no audio and the dashboard says "audio unavailable" (owners can retry with "Generate audio"); there is no local-voice fallback and nothing is written to disk. Audio is stored in Postgres (max 5 MiB per clip, pruned after `BRIEFING_AUDIO_KEEP_DAYS`); a failed regeneration keeps a clip of the same text, the same text and voice is never synthesized twice, and "Generate audio" is capped at 10 real syntheses per business per day. Legacy `/audio/<file>` rows are still readable by the old authenticated route and removed on erasure / retention.
- **An LLM is required in production.** `deploy.sh` refuses without an LLM key and `/api/health` answers 503 `llm_not_configured` (the container never becomes healthy). If the provider fails at runtime anyway, call summaries are stored as `[auto] <excerpt>` (shown as "Auto excerpt") and the briefing is the labelled automatic summary (`stats.narration = 'automatic'`, only counts, names, times and dollars). Website import answers 422 saying it needs the LLM.
- **`deploy.sh` has no `--seed`.** The demo dataset wipes every table and creates a fake live tenant, so it is refused in production (`scripts/seed.ts` also refuses `NODE_ENV=production`; the one-shot tools container of `compose.production.yaml` never seeds).
- **Onboarding progress** shows only real stages (reading + understanding the website is ONE request whose internal progress the server does not report, then saving): no timer-driven labels.

## Reviews 19-22: what is left after the fixes (`docs/review/19-22`, "Resolution" sections)

- **The platform's Twilio MASTER token is handed to the voice provider (report 19 F7).** Every import sends `TWILIO_AUTH_TOKEN` to ElevenLabs, which keeps it. A restricted API key or subaccount would be better but whether the import accepts one is unverified (check it in the live test, `docs/runbook.md` section 8). After a rotation run `repair-numbers` with `refresh_credentials` (the PATCH shape is unverified; fallback: delete the import and repair again).
- **No path switches a forward-mode tenant onto the native line (reports 19 F3 / 23 A5).** One guard (`lineImportBlockedReason`, inside `ensureTenantLine`) covers provisioning and a provision re-run, the agent re-sync after a 404 (`finishCreatedAgent`) and `repair-numbers`: such a tenant is reported `skipped` / `would_change_behaviour` until the operator moves it to AI / paused or enables native transfer for it; until its number is imported it keeps answering on our Voice URL and the dashboard says so.
- **A2P registration cannot be automated or fully detected (reports 20 H1 / 23 A2).** Registering the brand and the ONE platform campaign, creating the Messaging Service and setting its inbound handling to "Defer to sender's webhook" are manual (runbook section 5). With `TWILIO_MESSAGING_SERVICE_SID` the app adds every purchased number to the pool (idempotent, retried by `repair-numbers`), but a pool-membership failure leaves that number outside the campaign until it is repaired. Without the variable texts leave from unregistered tenant numbers: the app warns at boot and in `/api/health`, Twilio still answers 201, and a carrier filter is only visible through the status callback (`sms.delivery_failed` audit with the error code) and the Twilio console; nothing retries it. The Messaging Service request shapes (`messaging.twilio.com/v1/Services/{sid}/PhoneNumbers`, `MessagingServiceSid` with `From`, the `from` field of the send answer) are UNVERIFIED against a live account.
- **An ambiguous reply is answered neutrally and its words are not stored (reports 20 H1 / 23 A1).** A reply to a number that more than one business texted that customer from (the shared sender, or a Messaging Service pool number picked for another tenant) is matched ONLY by the recorded sender. With one candidate it goes to that business; with several, nothing business-specific runs (no "C" cancel, no 1-5 rating, no inbox row, no auto-reply), the customer gets a neutral acknowledgement, a STOP opts out every candidate (each sent from that number), and every candidate's owner is flagged (audit `sms.inbound_ambiguous`, one owner text per customer per 6 hours, no customer words). The customer's words are not kept anywhere, so such a customer may need to repeat themselves. Avoid it by pinning the sender (`TWILIO_MESSAGING_SERVICE_PIN_SENDER=on`). Rows written before migration `20261210120000` have no recorded sender and are never used for routing; a Messaging Service text whose sender has not been learned yet makes a reply to ANOTHER tenant's number ambiguous for 3 days.
- **The owner forward still carries up to 140 characters of the customer's text in the SMS the owner receives (report 20 H2/M3).** The platform's own log keeps none of it (export and erasure cover every copy it holds; rows written before this fix are matched by shape, last 4 digits and the opening words of one of the customer's own inbox texts, reproduced exactly as the forward was built: links masked, quotes swapped, clamped to GSM-7, so an emoji or non-Latin opening and the "Possible opt-out" variant are found too). Still NOT found (report 23 A8): a legacy forward whose inbox row was already deleted by retention (the shape alone cannot tell customers with the same last 4 digits apart: it ages out with the `sms_log` retention), and a text whose first 24 characters are only emoji / one non-Latin symbol that clamps to a single `?`. The SMS itself sits on the owner's phone and with the carrier, beyond any erasure by the platform. Links, domains and IPs are masked; a phishing sentence without a link can still reach the owner from the business line, which is why the text says "Customer text".
- **The migration rebuild of the overlap constraint locks `bookings` while its GiST index is built (reports 22 M1 / 23 A3).** Prisma runs each migration file as ONE transaction, so it now has a migration file of its own (`20261209120100_bookings_overlap_per_crew`) that holds no other lock, with a `lock_timeout`; the `sms_log` index is a single `CREATE INDEX CONCURRENTLY` statement in its own file; databases above about 100k bookings should deploy in a maintenance window (runbook section 4). The first version of `20261208120000` was edited before release: a database that applied it already has every part of the second migration (it is guarded).
- **No automatic opt-out for plain-language revocation (report 20 M2).** The text gets no automatic reply and the owner can opt the number out in one tap; the app does not opt out on its own because a phrase like "stop by at 5" is an ordinary message.
- **`clearContentConfirmation` is still never called (report 22 note).** A vertical switch that replaces the services changes the fingerprint, which has the same effect.
